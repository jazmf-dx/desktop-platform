# Recommendations

**現時点で推奨する crate / package の既定** をまとめた道標です。Standard ではありません。人と AI が同じ用途で毎回調べ直さず、かつメンテナンスされていないものを掴まないための参照先です。

## 1. 位置づけと拘束力

- 特に理由がなければ、ここに書かれたものを使う。
- 逸脱を禁止しない。別の選択をしてよい。
- 逸脱に ADR を求めない。選定理由を PR 説明へ短く残す程度でよい。
- ここに無い用途は各ツールで判断し、結果を §4 に従って追記する。

Recommendation は「現時点で何を選ぶか」を短く記録する。「どう実施するか」は [Playbook](../playbook/) に置き、ここへ重複して書かない。

## 2. ここに書かないもの

- Standard が既に答えているもの。CSP、更新の署名、データの置き場は [Standards](../standards/) が決めている。
- 採用実績のない候補、比較表、調査メモ。
- バージョン固定（lockfile の責務）、使い方のチュートリアル。

## 3. 依存の健全性チェック

未収録の crate / package を導入するときは次を確認する。

- リポジトリが動いているか。最終 commit と Issue / PR への応答を見る。
- アーカイブされていないか。
- ライセンスが許容範囲か（MIT / Apache-2.0 / BSD / ISC / Zlib 等）。GPL 系は再配布上の制約を個別に評価する。配布物に同梱されるので、Web アプリより重く見る。
- 既知の重大脆弱性がないか（`cargo audit`、`bun audit`）。
- 剥がすコストが局所的か。アプリ全体へ染み込む場合は導入判断を重くする。
- **バイナリの大きさとビルド時間への影響。** tokio / axum のような基盤を単機能のために入れない。
- **macOS と Windows の両方で動くか。** 片方だけなら `cfg` で分ける前提で載せる。
- 同じ用途のものが既にツールへ入っていないか。

最終リリース日だけで判断しない。安定した crate はリリース間隔が長くなる。放棄の判定はリポジトリの応答性で行う。

**AI agent への要求**：Recommendations に無い依存を追加する場合、導入前に上記チェックの結果を短く提示する。黙って追加しない。

## 4. 掲載条件

**実際に採用しているもの、または採用を決定して着手しているものだけを載せる。** 未検証の候補を載せない。候補を並べず、既定を 1 つに決めてから載せる。

## 5. エントリの書式

用途（やりたいこと）を見出しにする。各エントリは次を持つ。

- **既定**：名前と URL
- **ステータス**：`推奨` / `様子見` / `非推奨`
- **確認日**：実際に状態を確認した日付
- **採用**：使っているツール
- 適用範囲、使わなくてよい場面、併用するもの

| ステータス | 意味 |
|---|---|
| `推奨` | 特に理由がなければこれを使う |
| `様子見` | 継続利用してよいが、新規大規模採用の前に状態を確認する |
| `非推奨` | 新規採用しない。移行先を併記する |

## 6. 陳腐化の扱い

- 再確認は定期義務にせず、新規導入するとき・その領域を触るときに行い、確認日を更新する。
- `非推奨` になったエントリを削除しない。移行先とともに残す。
